1Syllabus, approach & HLD vs LLD

My 7-step interview approach

  1. Clarify requirements — functional + non-functional. Ask, don't assume.
  2. Estimate — users, QPS, storage, bandwidth (back-of-envelope).
  3. API design — main endpoints.
  4. Data model — entities, SQL or NoSQL.
  5. HLD diagram — client → LB → services → cache → DB.
  6. Deep dive — bottlenecks, scaling, single points of failure.
  7. Trade-offs — say what I gave up and why.

avg QPS  = 10^8 / 10^5     ≈ 1,000 QPS
peak QPS ≈ 2–3 × avg       ≈ 2,500 QPS
storage  = 1M photos/day × 500 KB ≈ 500 GB/day ≈ 180 TB/year

Revision

Requirements first (functional + non-functional) → estimate → API → data → HLD → deep dive → trade-offs. HLD = boxes & arrows; LLD = classes & schema.

2What happens when you open a website?

Big picture

Typing www.example.com triggers: DNS lookup → TCP connect → TLS handshake → HTTP request → servers → response → browser renders. This one flow touches almost every topic in this course.

Full stack request flow (L8)

Browser/ mobile app
→
DNSname → IP
→
CDNstatic files
→
Load Balancer
→
API / App server
→
CacheRedis
→
Database

→ response travels back the same way, browser paints the page

Step by step

  1. Browser cache check — already have the page / IP? use it.
  2. DNS resolution: browser cache → OS cache (hosts file) → recursive resolver (ISP / 8.8.8.8) → Root server → TLD server (.com) → Authoritative server → returns IP. Cached for its TTL.
  3. TCP 3-way handshake: SYN → SYN-ACK → ACK.
  4. TLS handshake (HTTPS): verify certificate, agree a session key (Ch 6).
  5. HTTP request: GET / HTTP/1.1 + headers + cookies.
  6. Static assets come from the CDN; dynamic request goes to LB → app server.
  7. App server checks cache; on miss queries the DB, fills cache, builds response.
  8. Browser renders: parse HTML → DOM, CSS → CSSOM, run JS → layout → paint.

DNS records

RecordMeaning
A / AAAADomain → IPv4 / IPv6 address
CNAMEAlias: one name → another name (www → example.com, or → CDN host)
MXMail server for the domain
NSWhich name servers are authoritative
TXTVerification, SPF/DKIM for email

Mobile app difference

The app already has its UI installed, so it skips HTML rendering — it only calls APIs that return JSON, then draws native screens. DNS/TCP/TLS/LB/server/DB steps are the same.

Mistake

"DNS is queried on every request" — no, answers are cached at many levels until the TTL expires. That's also why DNS changes take time to "propagate".

Revision

DNS (root → TLD → authoritative) → TCP → TLS → HTTP → CDN / LB → app → cache → DB → render. Be able to draw it in 30 seconds.

3Load Balancer

Definition

A load balancer sits in front of a group of servers and spreads incoming requests across them, so no single server is overloaded and a dead server gets no traffic. Real life: a traffic police officer sending cars to free lanes / a bank token system sending you to a free counter.

Why use one?

  • Scalability — add servers behind it (horizontal scaling).
  • High availability — health checks remove dead servers automatically.
  • No single server is a SPOF; zero-downtime deploys (drain one server at a time).
  • Can also do SSL termination, compression, caching (it's a reverse proxy — Ch 5).

Algorithms (interview favourite)

AlgorithmHowGood for
Round Robin1 → 2 → 3 → 1 → 2 … in turnEqual servers, similar requests
Weighted RRBigger server gets more turns (weights 3:1)Mixed server sizes
Least ConnectionsSend to server with fewest active connectionsLong / uneven requests
Least Response TimeFewest connections + fastest responseLatency-sensitive
IP Hashhash(client IP) % N → same user, same serverSticky sessions
RandomPick any healthy serverSimple, large pools

L4 vs L7

Layer 4 (transport)

Looks only at IP + port (TCP/UDP). Very fast, can't read URLs. e.g. AWS NLB.

Layer 7 (application)

Reads HTTP: URL, headers, cookies. Can route /api → API servers, /images → media. e.g. Nginx, AWS ALB.
nginx.conf
upstream app_servers {
    least_conn;                          # algorithm
    server 10.0.0.1:3000 weight=3;
    server 10.0.0.2:3000;
    server 10.0.0.3:3000 backup;
}
server {
    listen 80;
    location / { proxy_pass http://app_servers; }
}

Mistake

The load balancer itself can become the single point of failure. Fix: two LBs (active–passive with a floating IP) or a managed LB. Also: storing sessions in server memory breaks when the LB sends the user elsewhere → keep servers stateless, sessions in Redis.

Revision

LB = spread traffic + health checks. Algorithms: RR, weighted, least-conn, least-time, IP-hash. L4 = IP/port, L7 = HTTP-aware. Make the LB redundant too.

4CDN — Content Delivery Network

Definition

A CDN is a network of edge servers spread across the world that keep copies of content (images, videos, JS, CSS) close to users. A user in Delhi gets files from a Delhi/Mumbai edge instead of the origin in the US. Real life: Amazon warehouses in every city instead of one big warehouse.

How it works

User in India
→DNS / anycast
Nearest edgeMumbai PoP
→only on MISS
Origin serverUS
  1. DNS (often a CNAME to the CDN) sends the user to the nearest edge (PoP = Point of Presence).
  2. Cache HIT → edge serves the file instantly.
  3. Cache MISS → edge fetches from origin, stores it for the TTL, then serves. Next user nearby gets a HIT.

Push vs Pull CDN

TypeHowUse when
PullEdge pulls from origin on first request (lazy)Most websites; frequently changing, high traffic
PushI upload content to the CDN in advanceLarge, rarely changing files (video library, game patches)

Benefits

  • Lower latency — shorter physical distance.
  • Less load on origin + lower bandwidth bill.
  • Absorbs traffic spikes and DDoS (huge distributed capacity).
  • Availability — if one edge fails, another serves.

Cache invalidation

  • TTL via Cache-Control: public, max-age=31536000.
  • Purge API to delete a file from all edges.
  • Best: versioned file names — app.3f2a9c.js. New deploy = new name = no stale file.

Mistake

Caching personalised responses (my cart, my profile) on a public CDN → other users may see them! Use Cache-Control: private, no-store for user-specific data.

Revision

CDN = edge copies near users. HIT → serve, MISS → fetch origin + cache for TTL. Pull (lazy) vs Push (upload). Examples: Cloudflare, Akamai, AWS CloudFront.

Revision

Forward = for clients (hide client, filter). Reverse = for servers (LB, SSL, cache, security, hide servers). Remember who is hidden.

6SSL/TLS Certificates & HTTPS

Definition

HTTPS = HTTP + TLS (SSL is the old name). TLS gives 3 things: Encryption (nobody can read), Integrity (nobody can modify), Authentication (I'm really talking to bank.com). An SSL certificate is the website's digital ID card, signed by a trusted Certificate Authority (CA).

What's inside a certificate

  • Domain name(s) · organisation · public key · issuer (CA) · validity dates · CA's digital signature.

Chain of trust

Root CApre-installed in OS / browser
signs →
Intermediate CA
signs →
Server certexample.com

TLS handshake (simplified)

  1. ClientHello — TLS versions, cipher suites, random number.
  2. ServerHello + Certificate — chosen cipher, server's certificate (public key).
  3. Browser verifies the cert: signed by a trusted CA? domain matches? not expired?
  4. Key exchange (ECDHE / RSA) using asymmetric crypto → both sides derive the same session key.
  5. All data now encrypted with fast symmetric encryption (AES) using that session key.
PointAsymmetricSymmetric
KeysPublic + private pairOne shared secret key
SpeedSlowFast
Used forHandshake: identity + agreeing a keyBulk data after handshake
ExamplesRSA, ECDHEAES, ChaCha20

Certificate types

  • DV (domain validated, e.g. Let's Encrypt — free, 90 days) · OV (organisation checked) · EV (extended checks).
  • Wildcard *.example.com · SAN / multi-domain — many names in one cert.
terminal
# free cert + auto nginx config + auto-renew
sudo certbot --nginx -d example.com -d www.example.com
# inspect any site's certificate chain
openssl s_client -connect example.com:443 -showcerts

Mistake

"Padlock = safe website" — no. HTTPS only proves the connection is encrypted to that domain. A phishing site can have a valid certificate too. Also don't forget renewal — expired certs take sites down.

Revision

HTTPS = HTTP + TLS → encryption, integrity, authentication. Cert = domain + public key + CA signature. Handshake uses asymmetric to agree a key, then symmetric for data.

7Caching + Write-through vs Write-back

Definition

Caching = storing frequently used data in a faster layer (usually RAM) so we don't hit the slow source (DB / disk / network) every time. Real life: keeping a water bottle on my desk instead of walking to the kitchen each time.

Where caching happens

Browser cache
→
DNS cache
→
CDN
→
App memory
→
Redis / Memcached
→
DB buffer cache
  • Cache hit = found in cache. Miss = go to source. Hit ratio = hits / total — aim high (90%+).
  • Cache what is read often, changes rarely: product pages, user profile, config, sessions, results of heavy queries.

Read strategy — Cache-aside (most common)

cache-aside with Redis (Node)
async function getUser(id) {
  const key = `user:${id}`;
  const hit = await redis.get(key);
  if (hit) return JSON.parse(hit);              // 1. HIT → fast path

  const user = await db.users.findById(id);   // 2. MISS → DB
  await redis.set(key, JSON.stringify(user), 'EX', 3600); // 3. fill, TTL 1h
  return user;
}
// on update: write DB, then redis.del(key) so next read refreshes

Write strategies (L16)

StrategyHowProsCons
Write-throughWrite to cache AND DB together; ack after bothCache always consistent, no data lossSlower writes (2 writes every time)
Write-back
(write-behind)		Write to cache only, ack; flush to DB later in batchesVery fast writes, fewer DB hitsData loss if cache crashes before flush
Write-aroundWrite to DB only; cache filled on next readCache not polluted with write-once dataFirst read after write is a miss
Choose: bank balance → write-through (can't lose data). View counts / likes / analytics → write-back (speed matters, tiny loss is OK). Logs / bulk uploads → write-around.

Eviction policies (cache is small!)

  • LRU — remove Least Recently Used (most common). LFU — Least Frequently Used. FIFO — oldest first. TTL — expire after time.

Cache problems

ProblemWhatFix
Stale dataDB changed, cache still oldTTL + delete key on update
Stampede / thundering herdHot key expires → 1000s of requests hit DB at onceLock / single-flight, random TTL jitter
PenetrationRequests for keys that don't exist always missCache "null" briefly, Bloom filter
AvalancheMany keys expire at the same momentSpread TTLs, warm cache

From my work

TanStack / React Query on the frontend is a client-side cache (stale-while-revalidate) — same ideas: cache key, stale time, invalidation after a mutation.

Revision

Cache = fast copy. Cache-aside for reads. Write-through = safe, write-back = fast but risky, write-around = skip cache. Evict with LRU. Watch stale data + stampede.

An API (Application Programming Interface) is a contract that defines how one piece of software can ask another for data or actions — without knowing its internals. Real life: the waiter in a restaurant: I (client) order from the menu (API docs), the waiter takes it to the kitchen (server) and brings back food (response).

FastAPI in 5 minutes (L36)

  • Modern Python web framework for APIs, built on Starlette (async web) + Pydantic (validation).
  • Type hints → automatic validation + auto docs at /docs (Swagger) and /redoc.
  • async def support → high performance; dependency injection with Depends.
main.py — run: uvicorn main:app --reload
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI()

class User(BaseModel):
    name: str
    age: int                       # "abc" → automatic 422 error

@app.get("/users/{user_id}")
async def get_user(user_id: int):
    if user_id != 1: raise HTTPException(404, "Not found")
    return {"id": user_id, "name": "Sandeep"}

@app.post("/users", status_code=201)
async def create_user(user: User):
    return user

Revision

API = contract. REST (JSON, verbs, stateless), SOAP (XML, strict), GraphQL (ask exact fields), gRPC (binary, fast, internal), WebSocket (real-time). SDK = toolkit around an API. FastAPI = Python + type hints + auto docs.

9Horizontal vs Vertical Scaling

Definition

Scalability = ability to handle more load by adding resources. Vertical = make one machine bigger (scale up). Horizontal = add more machines (scale out).

Vertical ⬆

4 GB → 64 GB RAM, 2 → 32 CPUs.
Real life: replace a car with a bigger truck.

Horizontal ➡

1 server → 10 servers behind a load balancer.
Real life: more trucks in the fleet.
PointVerticalHorizontal
HowUpgrade CPU / RAM / diskAdd servers + load balancer
LimitHardware ceilingPractically unlimited
FailureSingle point of failureFault tolerant — one dies, others serve
DowntimeOften needs restartAdd/remove with no downtime
ComplexitySimple, no code changeNeeds LB, stateless apps, data distribution
CostHigh-end hardware gets expensive fastCommodity machines, pay as you grow
Data consistencyEasy (one machine)Harder (distributed)
Good forEarly stage, relational DB primaryWeb/app tier, large scale
  • Horizontal needs stateless servers: no session in memory → put sessions in Redis or use JWT.
  • Auto-scaling: cloud adds/removes servers based on CPU, request count (AWS Auto Scaling Group, Kubernetes HPA).
  • Real systems use both: scale up a DB first, then scale out with replicas / shards (Ch 10).

Mistake

"Horizontal is always better" — no. It brings network calls, consistency issues and ops overhead. Start simple (vertical) and scale out when needed.

Revision

Vertical = bigger box (simple, limit, SPOF). Horizontal = more boxes (LB, stateless, fault tolerant, complex). Use both.

10Partitioning · Sharding · Replication

Definitions

Partitioning = splitting a big table into smaller pieces (can be on the same server).
Sharding = horizontal partitioning where pieces live on different servers (shards).
Replication = keeping copies of the same data on multiple servers.

Horizontal vs Vertical partitioning (L10)

Horizontal (by rows)

Users 1–1M in P1, 1M–2M in P2. Same columns, different rows.

Vertical (by columns)

users(id, name, email) + users_profile(id, bio, photo). Split rarely used / heavy columns.

Partitioning strategies

StrategyHowProblem
RangeBy range: dates, IDs, A–M / N–ZHotspots (all new orders hit latest range)
Hashhash(user_id) % NEven spread, but adding a shard reshuffles most keys
ListBy category: region = India / US / EUUneven sizes
DirectoryLookup table: key → shardLookup service is extra hop / SPOF
Consistent hashingKeys & servers on a ring; key goes to next server clockwiseAdding a server moves only ~1/N keys ✓
MySQL range partition (same server)
CREATE TABLE orders (
  id BIGINT, created_at DATE, amount DECIMAL(10,2)
) PARTITION BY RANGE (YEAR(created_at)) (
  PARTITION p2024 VALUES LESS THAN (2025),
  PARTITION p2025 VALUES LESS THAN (2026),
  PARTITION pmax  VALUES LESS THAN MAXVALUE
);  -- WHERE created_at in 2025 → scans only p2025 (partition pruning)

Partitioning vs Sharding (L11)

PointPartitioningSharding
WhereUsually one DB serverMany DB servers
GoalFaster queries, easier maintenanceScale writes + storage beyond one machine
ComplexityHandled by DBApp/router must know which shard
Real lifeSeparate shelves in one librarySeparate library branches in each city

Sharding pain points

Bad shard key → hotspots (celebrity user). Cross-shard joins & transactions are hard. Resharding is painful → use consistent hashing. Shard only when you must.

Replication

→
Primary (master)
copies →
Replica 1
Replica 2

  • Primary–replica: writes to primary, reads from replicas → scales reads, gives failover.
  • Multi-primary: writes on many nodes → conflict resolution needed.
  • Sync = wait for replica (consistent, slower). Async = don't wait (fast, replication lag → stale reads).

Replication vs Sharding (L24)

Revision

Partition = split (same server). Shard = split across servers (scale writes). Replicate = copy (scale reads + HA). Pick shard key carefully; consistent hashing for resharding.

11CAP Theorem · ACID vs BASE

CAP theorem

In a distributed system, when a network partition happens you can guarantee only one of: Consistency or Availability.
  • Consistency — every read gets the latest write (all nodes show the same data).
  • Availability — every request gets a (non-error) response, even if not the latest.
  • Partition tolerance — system keeps working when messages between nodes are lost.
ChoiceDuring a partition…Use for
CPReject / block requests rather than return stale dataBank balance, payments, inventory/booking
APAnswer anyway, may be stale; sync later (eventual consistency)Social feed, likes, product reviews, DNS

Mistake

"Pick any 2 of 3" — in a real distributed system P is not optional (networks fail). The real choice is C vs A when a partition happens. Bonus: PACELC — Else (no partition) you trade Latency vs Consistency.

ACID (SQL transactions)

  • Atomicity — all or nothing. Consistency — rules/constraints always hold. Isolation — concurrent transactions don't interfere. Durability — committed = survives crash.
bank transfer — atomic
START TRANSACTION;
  UPDATE accounts SET balance = balance - 500 WHERE id = 1;
  UPDATE accounts SET balance = balance + 500 WHERE id = 2;
COMMIT;   -- any failure → ROLLBACK, money never disappears

BASE (many NoSQL)

  • Basically Available · Soft state (may change without input as replicas sync) · Eventual consistency (all replicas agree… eventually).
PointACIDBASE
PriorityCorrectness, strong consistencyAvailability, scale, speed
Typical DBMySQL, PostgreSQL, OracleCassandra, DynamoDB, CouchDB
ScalingMostly vertical (harder to distribute)Horizontal by design
ExamplePayments, orders, ledgersLikes count, feeds, analytics

Revision

CAP: partition will happen → choose C (CP) or A (AP). ACID = strict transactions (SQL). BASE = available + eventually consistent (NoSQL). Money → ACID/CP; social → BASE/AP.

Stores JSON-like documents; each can have different fields; nested data in one read.

  • MongoDB, CouchDB, Firestore
  • Use: product catalog, CMS, user profiles

2 · Key-Value DB (L18)

Simplest: key → value, like a giant hash map. O(1) lookups, often in-memory.

  • Redis, DynamoDB, Memcached
  • Use: cache, sessions, shopping cart, rate-limit counters, leaderboards
redis-cli
SET session:abc123 "user:7" EX 1800
GET session:abc123
INCR page:views:home
ZADD leaderboard 980 "sandeep"

3 · Column-Family DB (L19)

Rows identified by a key, columns grouped in families; each row can have different columns (wide rows). Data stored by column → great for huge write volume.

  • Cassandra, HBase, ScyllaDB
  • Use: time-series, IoT sensors, messages, activity logs
Cassandra CQL
CREATE TABLE messages (
  chat_id uuid, sent_at timeuuid,
  sender text, body text,
  PRIMARY KEY (chat_id, sent_at)
) WITH CLUSTERING ORDER BY (sent_at DESC);

4 · Graph DB (L20)

Data as nodes (entities) + edges (relationships). Following relationships is fast — no expensive multi-JOINs.

  • Neo4j, Amazon Neptune
  • Use: social network ("friends of friends"), recommendations, fraud detection, maps
Neo4j Cypher
// friends-of-friends I don't follow yet
MATCH (me:User {name:'Sandeep'})
      -[:FOLLOWS]->()-[:FOLLOWS]->(f)
WHERE NOT (me)-[:FOLLOWS]->(f)
RETURN f.name LIMIT 10;
Decision rule: money / relations / reports → SQL. Flexible docs → MongoDB. Speed / cache → Redis. Massive writes → Cassandra. Relationships → Neo4j. Big systems use several (polyglot persistence).

From my work

MySQL behind the Livia HMIS NestJS services (relational: patients, appointments, billing need ACID); MongoDB in the Cold Storage tool (flexible calculation inputs).

Revision

SQL = schema + JOIN + ACID. NoSQL = flexible + horizontal. Document (Mongo), Key-value (Redis), Column-family (Cassandra), Graph (Neo4j) — know one use case each.

13Message Queues

Definition

A message queue lets services talk asynchronously: a producer puts a message in the queue and moves on; a consumer picks it up and processes it later. Real life: restaurant order slips — the waiter pins the order and goes back to customers; the kitchen cooks at its own pace.
ProducerOrder service
→
[ msg | msg | msg ]Queue / Broker
→
ConsumersEmail · Invoice · SMS

Why use it?

  • Decoupling — producer doesn't know/care who consumes.
  • Buffer spikes — 10k orders/sec queue up; consumers process at their own speed.
  • Async heavy work — user gets "Order placed ✓" instantly; email, PDF invoice, notifications happen in background.
  • Reliability — if a consumer is down, messages wait; retries on failure.

Two models

Point-to-point

Each message is consumed by one consumer (work queue). e.g. resize image jobs.

Publish / Subscribe

14Microservice Architecture

Definition

Microservices = building an app as many small, independent services, each owning one business capability and its own database, deployed separately, talking over APIs/queues. Opposite: a monolith — one codebase, one deploy, one DB.
PointMonolithMicroservices
DeployWhole app every timeEach service independently
ScaleScale everything togetherScale only the hot service
FailureOne bug can crash allIsolated (if designed well)
TechOne stackEach team picks its stack
ComplexitySimple to start, debug, testNetwork calls, distributed data, monitoring, DevOps
Best forSmall team, early productLarge teams, large scale, clear domains

Building blocks

  • API Gateway — single entry: routing, auth, rate limiting, aggregation.
  • Service discovery — find service addresses dynamically (Consul, Kubernetes DNS).
  • Communication — sync REST/gRPC, async message queue / events.
  • Database per service — no sharing tables across services.
  • Resilience — timeouts, retries, circuit breaker (stop calling a failing service).
  • Observability — central logs, metrics, distributed tracing (correlation IDs).
  • Saga pattern — a distributed transaction as a chain of local steps + compensating actions (refund if shipping fails).

From my work

Livia HMIS: legacy PHP monolith → 7 NestJS microservices + MySQL, 48 modules migrated, keeping API contracts & business rules unchanged and checked with API parity tests (strangler-style migration).

Mistake

Distributed monolith — services share one DB or must deploy together. You pay microservice costs with none of the benefits. Also: starting a tiny project with microservices.

Revision

Small services, own DB, independent deploy. Gateway + discovery + async events + circuit breaker + tracing. Saga for cross-service transactions. Monolith first is fine.

16Rate Limiting

Definition

Rate limiting = controlling how many requests a client can make in a time window (e.g. 100 req/min per user/IP/API key). Extra requests get 429 Too Many Requests. Real life: an ATM daily withdrawal limit / OTP "try again after 30 s".

Why

  • Stop abuse: brute-force login, scraping, spam, DDoS. · Fair use between customers. · Protect DB/servers & control cost (paid 3rd-party APIs). · Pricing tiers (free 100/day, pro 10k/day).

Algorithms

Token bucketBucket holds N tokens, refilled at fixed rate. Each request takes 1 token; empty → reject.✓ Allows short bursts, memory-light. Used by AWS, Stripe.
Leaky bucketRequests enter a queue, processed (leak) at a constant rate; full → drop.✓ Smooth output. ✗ Bursts wait / dropped.
Fixed window counterCount per window (12:00–12:01); reset each minute.✓ Simple. ✗ Boundary burst: 100 at 12:00:59 + 100 at 12:01:00.
Sliding window logStore timestamp of each request; count those in last 60 s.✓ Accurate. ✗ Memory heavy.
Sliding window counterCurrent count + previous window × overlap %.✓ Accurate enough + cheap (best balance).

async function rateLimit(req, res, next) {
  const key = `rl:${req.ip}:${Math.floor(Date.now() / 60000)}`;  // per minute
  const count = await redis.incr(key);
  if (count === 1) await redis.expire(key, 60);
  res.set('X-RateLimit-Remaining', Math.max(0, 100 - count));
  if (count > 100) return res.status(429).set('Retry-After', '60').send('Slow down');
  next();
}

Mistake

Keeping counters in each server's memory — with 5 servers behind an LB the user really gets 5× the limit. Use a shared store (Redis). Also rate-limit login/OTP endpoints much tighter than normal ones.

Revision

Limit requests per key per window → 429 + Retry-After. Token bucket (bursts), leaky bucket (smooth), fixed window (simple, edge burst), sliding log/counter (accurate). Shared counters in Redis.

Defense in depth (L21)

Never rely on one lock. Put security at every layer, so if one fails the next stops the attacker. Real life: a bank — guard at the gate, CCTV, ID check at the counter, locker with a key + PIN.
LayerWhat protects it
NetworkFirewall, VPC / private subnets (DB not public), security groups, DDoS protection (Cloudflare / AWS Shield)
TransportHTTPS / TLS everywhere, HSTS
ApplicationAuthentication + authorization, input validation, parameterised queries (SQL injection), output escaping (XSS), CSRF tokens, WAF, rate limiting
DataEncryption at rest, hash passwords (bcrypt/argon2 — never plain/MD5), least-privilege DB users, backups
MonitoringAudit logs, alerts, intrusion detection, dependency scanning
AuthN (authentication) = who are you? (login). AuthZ (authorization) = what are you allowed to do? (roles: admin / doctor / patient). 401 = not authenticated, 403 = authenticated but not allowed.

JWT — JSON Web Token (L31)

Header{alg:"HS256",typ:"JWT"}
.
Payload{sub:7, role:"admin", exp}
.
SignatureHMAC(header.payload, secret)
  • 3 parts, each Base64URL-encoded, joined by dots: xxxxx.yyyyy.zzzzz.
  • Payload is signed, NOT encrypted — anyone can decode it. Signature only proves it wasn't tampered with.

res.cookie('refresh', refresh, { httpOnly: true, secure: true, sameSite: 'strict' });

// middleware → verify on every request
const token = req.headers.authorization?.split(' ')[1];   // "Bearer <token>"
try { req.user = jwt.verify(token, ACCESS_SECRET); next(); }
catch { res.status(401).send('Invalid or expired token'); }

NextAuth in the Marriage Registration portal (session handling); PayU flow where the server builds and verifies the hash — never trust amounts or status coming from the browser.

Putting passwords / secrets in the JWT payload (it's readable!). Storing tokens in localStorage → stolen by XSS; prefer httpOnly, secure cookies. Never skip checking exp and the algorithm.

The problem

  1. Absorb the spike at the edge — static pages, train lists and schedules from CDN / cache; login done before 10:00.
  2. Rate limiting + CAPTCHA + bot detection — stop scripts and agents spamming requests; limit per user/IP.
  3. Virtual waiting room / queue — users get a place in line; only as many as the booking servers can handle are let in. Smooth load instead of a crash.

21Case study — UPI

What is UPI?

Unified Payments Interface — India's real-time, 24×7 bank-to-bank payment system run by NPCI. Pay using a VPA / UPI ID (name@okbank) or QR code — no account number / IFSC needed.

The actors

ActorRole
Payer app (TPAP)PhonePe, Google Pay, Paytm, BHIM — the UI on my phone
PSP bankPayment Service Provider bank behind the app; connects the app to UPI, owns the @handle
NPCI UPI switchCentral router: resolves VPA → bank account, routes debit/credit, keeps the records
Remitter bankMy bank — verifies UPI PIN, debits my account
Beneficiary bankReceiver's bank — credits their account

Payment flow (send ₹500)

  1. I enter the payee VPA + ₹500 + UPI PIN. The PIN is encrypted on the device (NPCI common library) — the app never sees it in plain text.
  2. App → PSP bank → NPCI switch with a unique transaction ID.
  3. NPCI resolves payee VPA and sends a debit request to my bank → bank verifies PIN, checks balance, debits.
  4. NPCI sends a credit request to the beneficiary bank → credits payee.
  5. Success travels back to both apps in seconds; both get notifications.

System design ideas inside UPI

  • Idempotency — every transaction has a unique ID; retries never debit twice.
  • Strong consistency (CP / ACID) for money: debit + credit must both happen, or the debit is reversed.
  • Timeouts & deemed status — if a bank doesn't respond, the transaction goes to "pending" and is resolved by status checks + reconciliation; failed debits are auto-reversed.
  • Security — device binding (SIM + phone) + UPI PIN = 2-factor; everything over encrypted channels; per-transaction & daily limits.
  • Scale & availability — billions of transactions/month, 24×7; NPCI switch is horizontally scaled with redundant data centres; bank downtimes are isolated.
  • Interoperability — any app ↔ any bank through one central switch (hub-and-spoke), like a standard API contract.

Mistake

Thinking the app (PhonePe/GPay) holds my money — it doesn't. Money moves bank → bank; the app is only the interface, NPCI is the router.

Revision

App → PSP → NPCI (resolve VPA) → remitter bank (PIN + debit) → beneficiary bank (credit). Unique txn ID = idempotent. Money = consistency first, reversals + reconciliation. Device binding + PIN.

22Rapid-fire Q&A

Q. What happens when you type a URL?

A. DNS → TCP → TLS → HTTP → CDN/LB → app → cache → DB → response → render.

Q. Load balancer vs reverse proxy?

A. LB spreads load across many servers; a reverse proxy fronts servers (SSL, cache, security). Every LB is a reverse proxy.

Q. Which LB algorithm for long-lived uneven requests?

A. Least connections.

Q. How does a CDN reduce latency?

A. Serves cached copies from an edge server physically near the user; only misses go to origin.

Q. Write-through vs write-back?

A. Write-through writes cache + DB together (safe, slower). Write-back writes cache, flushes later (fast, risk of loss).

Q. What is cache stampede?

A. A hot key expires and many requests hit the DB at once — fix with locking / single-flight and TTL jitter.

Q. Horizontal vs vertical scaling?

A. Vertical = bigger machine (limit, SPOF). Horizontal = more machines (needs LB + stateless apps).

Q. Sharding vs replication?

A. Sharding splits data (scale writes/storage); replication copies data (scale reads, HA). Use both.

Q. Why consistent hashing?

A. Adding/removing a node moves only ~1/N keys instead of reshuffling everything.

Q. CAP in one line?

A. Partitions will happen, so choose consistency (CP) or availability (AP) during one.

Q. ACID vs BASE?

A. ACID = strict transactions, strong consistency. BASE = basically available, eventually consistent.

Q. When NoSQL over SQL?

A. Flexible schema, massive scale / write volume, simple access patterns. SQL for relations, transactions, reporting.

Q. Why a message queue?

A. Decouple services, absorb spikes, do slow work async, retry safely.

Q. At-least-once delivery means…?

A. Messages can repeat → consumers must be idempotent; failed ones go to a DLQ.

Q. When NOT to use microservices?

A. Small team / early product — a modular monolith is simpler; split later along clear domains.

Q. WebSocket vs SSE?

A. WebSocket is two-way; SSE is one-way server → client over plain HTTP.

Q. Best rate-limit algorithm for bursts?

A. Token bucket.

Q. Is JWT encrypted?

A. No — signed. Anyone can read the payload; the signature only prevents tampering.

Q. How to log out a JWT user?

A. Short-lived access token + revocable refresh token (or a denylist).

Q. HLD vs LLD?

A. HLD = components & data flow; LLD = classes, methods, schema inside each component.

Q. How to prevent double booking?

A. Atomic conditional update / row lock on inventory + temporary hold + release on timeout.
